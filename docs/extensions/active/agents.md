# agents

**Historical proof boundary (T-111):** 2026-06-17 evidence used the former
replacement-session `/agent run --yes` / `--approve` implementation and showed
session switch-back. It remains historical evidence only. Current `/agent run`
does not replace the parent session: it uses the shared `createAgentSession` SDK
child, live row, progress panel and run boundary described below.

## Purpose

`agents` — default-loaded operator/catalog extension. It registers the `/agent` command through `package.json#pi.extensions`, imports agent definitions from `.agents/agents/*.md` and shows diagnostics for invalid files.

`/agent run <name> <task>` starts one command-side SDK child through `createAgentSession` and the same `executeAgentRunBoundary` used by the tool path. The flags `/agent run --yes <name> <task>` and `/agent run --approve <name> <task>` are kept as legacy trusted-operator syntax, but the local Locus approval prompt no longer runs. The command creates a shared live row, shows progress and writes a result artifact without a parent-session switch. The `spawn_agent` and `task` tools accept one required `task` string, an optional `agent`, an optional `title` and an optional `parentContext`; a single call creates exactly one child agent. On success `ToolResult.content` contains the exact final text of the child. Technical fields stay in `details`. Both paths fail closed when the host does not export `createAgentSession`, when the final text is empty, or when the child run actually ended in an error. The aliases `default -> task` and `general -> task` are kept; `general` is a built-in alias only when the project/user catalog does not contain a real `.agents/agents/general.md`.

## Why it is in the project

`locus-pi` owns the catalog layer and the shared SDK child-session adapter for slash/tool triggers. This is a deliberate boundary: the operator can inspect agent definitions and the live command path, while the model-callable `task` runs agents through the same host contract with safety, timeouts, cancellation and durable evidence.

The old deterministic accepted-task summary was dangerous because it looked like a successful agent run even though no model and no subprocess were actually created. The current runner accepts `completed` only after a real child turn and a non-empty answer. Tool calls, the JSONL transcript and `locus_workload_proof` remain evidence, but a reasoning-only answer without a tool call is valid.

## Surface contract

- The operator runs `/agent list` to see the loaded markdown definitions. In the TUI the full typed `VIEW` opens in the shared inline scroll surface at the editor (`overlay:false`). RPC and hosts without custom UI get a compact passive preview with source counts, `+N definition(s) hidden` and the inspect/run commands, so a host limit does not hide the recovery action.
- The operator runs `/agent inspect <name>` to see a typed `VIEW` with source, file path, tools, read-only status, risk, spawn policy and model hints for a single definition. A known definition uses the same inline TUI surface; an unknown target stays a bounded `ERROR`, shows source-priority candidates, built-in aliases, the `/agent list` recovery and the path of the diagnostic artifact.
- The operator runs `/agent run <name> <task>` to start one SDK child in the current parent-side live surface without a session switch. Pi native approval handles child tool prompt/deny decisions; `/agent run --yes` and `/agent run --approve` are retained legacy trusted-operator forms. Headless/fallback completion uses typed `RESULT` or `ERROR` chrome with child/result evidence and drill command. The working TUI progress panel stays a separate domain-owned `LIVE` surface and is not replaced by a static renderer. The command shows `completed`, `failed`, `cancelled` or `blocked`. The unknown-agent error is rendered in the `agents` widget, shows the available agents, built-in aliases, the `/agent list` hint, and writes a diagnostic artifact to `.locus/runtime/artifacts/*.json`.
- Unknown or incomplete `/agent` syntax returns typed `WARN` with a no-action statement and the exact relevant usage. It does not leave recovery as an equal-weight notification.
- The operator runs `/agent observe` or `/agent summary` to see a bounded snapshot of the current and recent live rows without a background daemon. Rows show source-backed status, elapsed time, activity state, concrete runtime model plus `/effort` thinking level when available, current path, current tools, bounded tool args, turn/token counts, child session, result artifact, final answer, flags, and errors. `steps` is rendered as event count, `turns` as model turns, and `flags` include inline meaning such as `no-mcp(no MCP tools)` so the row is readable without source code. `done`, `cancelled` and `error` rows stay terminal, not running. Any terminal transition atomically clears `currentTools`, `currentToolArgs` and `currentToolStartMs`, and also freezes `elapsedMs`, so the drill does not show a stale command and the duration no longer grows after completion.
- `/agent list`, `/agent inspect`, `/agent observe`, and `/agent summary` render transient `agents` widgets. Shared command UI lifecycle clears that widget and `agents` status on the next unrelated user input or slash command; related `/agent ...` input is left alone so the command can replace the widget. `/devext doctor` now gets the same cleanup through the shared lifecycle instead of owning an `agents` special case.
- While live rows exist, ordinary agent runs keep their expanded passive fleet below the editor, while workflow runs keep their separate compact current-row projection. Bare `Up`/`Down` (`↑/↓`) always belong to Pi for cursor/history/editor and the extension does not intercept them. `/ps` or the registered `Shift+Down` opens the one focused selector owned by the agents extension; it derives its current global rows directly from `agentLiveStore`, so passive widget render order cannot hide another agent family. Once focused, `↑/↓` move the selection. Aggregate/group rows are visible as headings, but are not selectable by the cursor and are not accepted by `Enter`, `x` or `last`; a direct aggregate id yields guidance to pick a single child agent. `Cmd+Down`, `Ctrl+Down` and the former `Alt/Option+A` are not registered and not shown. Installed-Pi tmux mid-run proved the fallback `Shift+Down → focus → arrows → Enter → drill`. `Enter` opens the drill, and `x` first shows a Yes/No confirmation and only after confirmation sends a real abort to the selected SDK child. `Esc` inside the fleet or the drill closes only the view; the notification states explicitly that the active agent keeps running. If a bare `Esc` would reach the standard Pi `app.interrupt` during a parent turn with live agent rows, the extension asks for confirmation first; a refusal leaves the operation running, a confirmation calls `ctx.abort()`. In RPC an updatable passive `string[]` widget remains, without false controls.
- Pi owns a single non-overlay editor slot: mounting a component runs `editorContainer.clear()` and the component already there is detached without `dispose()` and without its `custom()` promise ever settling. The shared inline interaction surface therefore models the same rule — the newest interaction that is actually able to mount takes the slot, and the one it replaced is failed with a superseded error so its owner can drop its UI state instead of awaiting a component nobody can see. A request that cannot mount (stale caller lease, no custom UI) never supersedes: it waits its turn and leaves the live component alone, so a declined question cannot take an open fleet selector off the screen. Without this, one replaced component held the surface for the rest of the session and every later `/ps` or operator question silently did nothing. The stale host promise for a replaced component is deliberately left pending: Pi's own close path restores the editor, which would clear whatever replaced it. Leaving that promise pending is not enough on its own, because the replaced component still holds the callback Pi handed it — an `ask.timeout`, an abort listener, or a queued key can call it later, and Pi's `close` then runs `editorContainer.clear()` plus a re-added editor over whichever interaction is on screen now. That is why the shared surface fences the callback by slot ownership: a request that no longer owns the slot drops the call and disposes its own component, so a superseded prompt cannot blank an open `/ps` fleet and leave the command looking like it did nothing. For the same reason the slot changes hands only once the newcomer's factory has actually produced a component: Pi mounts after the factory fulfils, so a request that never appears cannot take the slot from a live surface. A factory that _rejects_ is a different case, and the honest one: Pi runs its own `restoreEditor()` on that path, so the live component is off the screen whether or not the newcomer wanted the slot. The incumbent is therefore explicitly retired there too — it learns the surface is gone through the same superseded error any takeover produces, instead of awaiting a component nobody can see.
- The operator runs `/ps` for fleet selection or `/ps <row-id|agent|petname|last>` to jump directly. `/agent ps` is the stable fallback on a collision, `/agent drill` is a compatibility alias. The resolver keeps the exact/normalized/ambiguity rules. The selected row opens in the shared inline editor-replacement surface, never over scrollback. The viewer uses the Pi `AssistantMessageComponent`/`ToolExecutionComponent`, follow-tail, manual scroll, `End`, compact/expanded tools and `Esc`/`q` return without abort. The fleet shows the last visible assistant message; raw args/stdout/event names stay detail/diagnostics.
- The main agent or the workflow runtime can call the primary tool `spawn_agent` (back-compat alias `task`) with an optional `agent`, a required `task`, an optional `title` and an optional top-level `parentContext`. If `agent` is absent or equals `default`, the runner picks `task`; if `agent` equals `general`, the runner picks `task` only when there is no real project/user `general`. One call spawns one headless child through `createAgentSession`. Success returns the exact non-empty child text in `ToolResult.content`; JSON-like text is not parsed. Unknown-agent and child-session failures are returned with `isError=true`, readable `content` and technical `details`.
- The `agent` parameter of `spawn_agent`/`task` advertises the catalog it accepts. Its description carries the resolved first-match-wins agent set as bounded `name — description` lines, so the caller selects a name from a visible list instead of guessing one. The list is bounded twice — at most 12 entries, each description clamped to 96 characters — and states its own overflow as `+N more — /agent list`, ordered project, then user, then bundled, so a locally authored agent is never the entry that falls off the cap. The catalog is not a permission check: it reduces wrong guesses, and an unknown name is still refused by the unchanged unknown-agent path with its available-agent list and diagnostic artifact.
- A child agent cannot directly spawn another child agent. The SDK host always passes `excludeTools: ["spawn_agent", "task"]`; Pi applies that deny after any `tools` allowlist, so `tools: ["*"]`, an explicit `task` or legacy `spawns` metadata do not bypass the ban. Bundled profiles no longer declare `spawns`. The parser keeps legacy/project `spawns` only for catalog compatibility and marks it as blocked. At the same time `workflow` is deliberately not excluded: a child can write `.pi/workflows/*.workflow.mjs` and call the `workflow` tool if its profile allows that tool; the workflow runtime already owns orchestration and separate child rows.
- The token counter is updated on every `turn_end` from the real assistant `usage.input + usage.output`, so `↓<tok>` appears before the agent finishes. The final `getSessionStats().tokens` replaces the intermediate value with the cumulative truth. Every child keeps its own counter; the summary row for a `parallel`/`pipeline` workflow recursively sums token-bearing descendants without counting group rows twice.
- The only output contract of an agent is text. The runtime does not recognize a marker, result envelope, status, summary, diagnostics or artifacts inside the model answer. Empty text is failure. JSON is needed by separate calling code only through an explicitly chosen non-agent protocol.
- The legacy tool `runAgent` is removed from the active surface. The `/agent run` command stays the only command-gated run path.
- An agent or a reviewer flow can call `locus_workload_proof` to record diagnostic persisted evidence after a bounded child workload. This tool is not an execution engine and does not control success/failure by itself.

## How it works in code

The entrypoint `extensions/agents/index.ts` wires the per-session state (session epoch, fleet-menu controller, fallback focus shortcut) and calls the registration functions: `command-router.ts` registers the `agent` and `ps` commands through the shared `registerCommandWithUiLifecycle`, `task-tool.ts` registers the primary tool `task`, and `workload-proof-tool.ts` registers `locus_workload_proof`. Before command/tool calls the extension refreshes the list of definitions through `_shared/agent-runtime/agents.ts` from a single convention: the nearest project `.agents/agents`, the user `~/.agents/agents`, then the bundled `.agents/agents` inside the package. The merge rule is first wins, so project definitions override user and bundled agents, and user definitions override bundled agents.

Every refresh republishes the caller-facing catalog: `refreshAgents` formats the resolved definitions through `formatAgentCatalogHint` in `_shared/agent-runtime/agents.ts` and writes the result onto the `agent` property of the shared `TaskParams` schema, which `spawn_agent` and `task` both register. The parameter schema is the injection point because Pi hands `ToolDefinition.parameters` to the model provider by reference on every request, while it snapshots `description` when the tool is wrapped — so the schema field is the one place that is both next to the decision and refreshable without re-registering the tool. A `before_agent_start` hook runs one refresh per turn, so an agent added to `.agents/agents/` mid-session is selectable without a restart instead of being frozen at registration time.

The parser accepts YAML-like frontmatter, sufficient for a local catalog. It keeps `name`, `description`, `tools`, legacy `spawns`, `model`, `thinking-level`, `blocking`, `output`, `systemPrompt`, `source` and `filePath`. `spawns` is only compatible catalog metadata and does not grant a runtime capability: direct nesting is always blocked by the SDK host. Nested `output` stays opaque metadata. Invalid markdown or missing required fields end up in diagnostics and do not become runnable definitions.

`readOnly: true` is a runtime capability boundary, not just a description.
The SDK host keeps only `read`, `grep`, `find`, `ls`, `yield` and an explicitly
requested `git_read`; it removes `bash`, `write`, `edit`, `workflow` and unknown
tools. `git_read` runs Git without a shell and accepts only allowlisted
query subcommands. Mutations, writing an output file, external diff, textconv, pager,
signature and runtime config options are blocked before the process starts.

The tool execution path is working. `task` calls `_shared/agent-runtime/agent-runner.executeAgentRunBoundary` with the tool-context executor `createAgentSdkSessionExecutor` (`_shared/agent-runtime/agent-sdk-host.ts`), which spawns a headless child through the host-SDK `createAgentSession`, waits for `agent_end`, reads `getSessionStats()`, exports the JSONL transcript and takes the last non-empty final answer without JSON parsing. The runner still checks depth, maxTurns and the tool allow-list; approval prompt/deny decisions belong to Pi native approval before the tool handler runs, not to this runner. Nested `createAgentSession` receives `cwd`, allowed tools, model and optional `appendSystemPrompt`; no confirmed Pi SDK option is used here to inherit parent yolo/approval policy into the child session. When the host does not export `createAgentSession`, `task` honestly fails closed (`agent-sdk-session-unavailable`). When the child run returns `failed`, `blocked` or `cancelled`, `task` returns `isError=true`. A non-empty `parentContext` is passed into the single `createAgentRunRequest`; empty or absent context is not forwarded. The details contain `parentContextBroker: { forwarded, sources, agentDefault }`. If the definition has a `systemPrompt`, the SDK path appends it through `DefaultResourceLoader.appendSystemPromptOverride`, to keep the base Pi prompt and tool semantics.

Pi loads every package entrypoint with a separate `jiti` with the module cache disabled. Therefore a module-local singleton is not a cross-extension contract: `agents` and `workflows` used to get different `agentLiveStore` instances, and a workflow row was visible in progress but not in `/agent drill`. The store now lives in a versioned `globalThis[Symbol.for(...)]`; a separate regression test loads producer/consumer with two real Pi entrypoints and proves the shared row. On `session_start` the store is cleared, so process scope does not turn rows of a previous session into current ones.

`buildAgentSystemPrompt` is optionally extended with a context extras block, only when `LOCUS_AGENT_CONTEXT_EXTRAS=1`. By default extras are off. The memory extras come from `LOCUS_AGENT_MEMORY_FILE` or `<projectRoot>/MEMORY.md`; the skill extras come only from explicit `LOCUS_AGENT_PRELOAD_SKILLS` entries and are resolved by the strict paths `.agents/skills/<name>/SKILL.md` or `.pi/skills/<name>/SKILL.md`. Both blocks are bounded: memory takes the first 200 lines and a byte cap, skills are clamped too, and missing files become diagnostics and do not fail the child run.

`/agent run` calls `runAgentLiveTask()`, which creates a row in the process-shared `agentLiveStore`, builds a deterministic request capsule with resolved model-role metadata, and starts `createAgentSdkSessionExecutor()`. The executor uses the host-SDK `createAgentSession`, adds the persona through `DefaultResourceLoader.appendSystemPromptOverride`, reads the real child events/stats/final answer and returns the final answer as exact text. The parent-session `ctx.newSession` and `pi.sendUserMessage` are not used in the current command path.

`/ps` and its compatibility aliases open `AgentSessionViewer` only in interactive TUI with native Pi component capability. One bounded typed timeline owns stable assistant/tool blocks, structured lifecycle, `cwd`, redaction, `latestMessage`, 100 content items per message, and aggregate `512 KB`/`5000` node limits. Raw `eventLines` remains diagnostic-only. RPC/headless receives honest passive fallback; historical workflow rounds retain journal summary fallback. Global input guards yield while viewer owns the terminal, native tool components update only on state transitions, and listener/component cleanup is idempotent.

Live-row rendering is shared with workflow views through `_shared/agent-runtime/agent-live-panel.ts`. The shared renderer owns row ordering, bounded text formatting, concrete model plus `/effort` display, activity labels, path display, tool-argument clamping, group summaries, and optional child-result fields. `/agent observe`, `/agent summary`, `/agent drill`, `/workflows run`, and the headless workflow `liveAgents` fallback all read from the same local `AgentLiveRow` contract instead of copying separate row formatters.

Workflow runs add only a workflow-specific stage projection around that shared
row contract. The passive below-editor view keeps one compact active child and
the declared/reached/current stage frontier; `/ps` reuses the full fleet and
viewer. Parallel groups are context-only headings, while `Enter`, `Esc`, and
confirmed `x` keep the same leaf drill/return/cancel semantics as ordinary
agent runs. A replayed child without a transcript is rendered from its
digest-verified answer artifact, never from fabricated session output.

## Limitations and risks

This extension runs one `task` with one child agent. The batch `tasks:[]` is removed; parallel orchestration belongs to the workflow `parallel()`. `/agent run` is useful as a local catalog inspect surface, a command-side SDK live runner, a result-artifact writer and a proof path. `task` is a working execution tool with a genuine child workload and an exact text result.

A non-empty text result without workload proof can be a success. Tool calls, tool results, transcript proof and persisted `locus_workload_proof` remain diagnostic evidence, but are not a mandatory condition for `completed`. Durable unknown-agent artifacts are diagnostic evidence only; they do not prove a child run happened.

`/agent observe` / `/agent summary` are an on-demand local live-store summarizer. They read a bounded snapshot from `agentLiveStore.rows`, show total + status counts, bounded recent rows, bounded event digests, and optional row metadata when current code has a real source for it. `done`, `cancelled` and `error` rows stay terminal, not running, with no stale tool args. `observer` is not full pi-subagents parity: it is a local summarizer over live rows, not a background daemon.

The viewer gives native Pi presentation parity for observation, but not a literal session handoff: the parent runtime keeps owning child execution. A child editor, slash commands, model/settings and `switchSession()` transfer are not claimed.

Terminal assistant `stopReason: "error"` surfaces its `errorMessage` before the generic empty-result fallback. A `completed` child still requires a real non-empty answer; side-effect-only success and DSL changes are outside this extension contract.

## Decision

Decision: `default-command-gated-single-agent` + a tool-safe `task` through the host-SDK `createAgentSession`. `agents` is in `package.json#pi.extensions`; `task` is covered by the retained SDK-host tests and the installed-package Pi smoke, and no new entrypoint was added.

## Agent profiles — when to use default vs scout

`default` is the general reasoning and delegation profile. Use it when the caller needs an owner-default child agent for broad delegated workflow steps and does not need runtime evidence. Its bundled profile sets `evidence.mode: none`.

`explore` is the read-only scout profile. Use it for fast codebase investigation and handoff context. It is expected to call at least one tool; the bundled profile sets `evidence.mode: warn` and `requireAnyToolCall: true`, so an empty tool trace produces a warning.

`task` is the full-tool worker profile. Use it for delegated implementation or multi-step work that may need file edits, shell commands, or other tools. Its bundled profile sets `evidence.mode: warn` and `requireAnyOf: [bash]`, so a run with no observed `bash` call produces a warning. Named-tool evidence comes only from exact `tool_execution_start/update/end` events seen by the SDK child subscriber, normalized by trim/deduplication/stable sort and transported as `AgentChildOutputStats.recordedToolNames`. Aggregate `toolCalls`/`toolResults` still prove that some workload occurred, but never fabricate a specific tool name; counters without a named event therefore cannot satisfy `requireAnyOf: [bash]`.
